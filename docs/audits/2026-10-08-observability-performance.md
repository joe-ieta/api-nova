# OBS-16-04 本机真实链路性能测量与调度修复

> 后续批处理、源完整性与SQL.js整改结果见[2026-10-08联合吞吐证据](2026-10-08-observability-throughput-closure.md)。本文保留上一阶段实测；当前整体状态仍未签收。

本轮使用独立数据库、随机回环端口、真实管理认证与 Gateway 认证调用，自动启动生产 collector、outbox 和 webhook Worker。不是手动调用 `runOnce`，不是向数据库注入事件后测发送器。正式生产签收仍待办，性能门槛保持[原批准要求](../guides/runtime-observability-requirements.md)不变。

## 可复跑入口与口径

入口：[verify-obs-16-04-performance.cjs](../../scripts/verify-obs-16-04-performance.cjs)。先构建 parser/API；`node scripts/verify-obs-16-04-performance.cjs` 使用独立 SQLite（实际 SQL.js、autoSave=true）；增加 `--postgres` 创建独立 PostgreSQL 集群（需 initdb/pg_ctl 在 PATH 或设置 API_NOVA_TEST_PG_BIN）。不连接现有 5432。`--smoke` 为 2 请求/秒配置联通检查，不能替代正式性能。

默认正式负载为 100 请求/秒、30 秒、3000 次 GET，请求正文 0 字节，固定 JSON 响应 4024 字节，启用默认正文采集。随后观察最多 60 秒，另执行每类 20 次授权明细、列表与汇总查询。`OBS_PERF_DURATION_SECONDS` 可设 10～120，`OBS_PERF_TAIL_SECONDS` 可设 10～300；结果必须同时记录持续时间与容量。每个外部 Gateway 请求生成普通 `invocation.completed` 订阅事件，受控 HTTP 回环接收端逐次验证 HMAC 并返回 202。HTTP 例外只供本机性能隔离，生产 TLS 另有[信任验证](2026-10-08-observability-signoff-readiness.md)。

- 采集可见性：实际授权 HTTP 列表首次看到终态的时间减记录 `completedAt`；100 ms 轮询间隔及查询本身构成观测上界。
- 首次报送：普通事件的接收时间减 `occurredAt`（实现中取调用完成时间）；比首次尝试开始略晚，作为保守上界，不使用 subscription-test 事件。
- 分位数：排序后 nearest-rank p50/p95/p99。存在未观察/未接收样本时只列已见子集分位数与 censored 数，禁止据此宣称整体通过。
- 固定基准采集额外 p95：**未测**。关闭 collector 不等于关闭业务 instrumentation，直连 upstream 又包含认证/路由差异，均不能冒充等价 A/B。单独卸载 Gateway ingress 采集也不覆盖 upstream instrumentation。
- 机器、Node/DB、候选 HEAD、锁文件、源码与构建 Worker hash、调度偏差、查询实际容量、资源曲线保存在每次 evidence。资源曲线限宿主 CPU/free memory 与压测进程内存，不冒充 API 进程内存。主机未限制为批准参考 4 核/8 GiB，磁盘 SSD 类型也未独立核验；短时测试不证明长期稳态。

## 调度前真实发现

配置 smoke：`.tmp/obs-16-04-performance-2xrek4/evidence.json`，2 请求/秒、20 次业务调用和20次签名接收均成功；可见性 p95 5587 ms，首次接收 p95 6525 ms。该轮与其他验证并行，只证明链路及瓶颈线索，不作正式性能结论。

正式旧构建基线在其他测试与恢复演练结束后运行：`.tmp/obs-16-04-performance-iWzg9U/evidence.json` 和 `api.log`。3000 次请求在 30.002 秒发出（99.993 请求/秒），1486 次 HTTP 成功、1514 次失败/超时，成功子集业务 p95 为 43962 ms。API 最终因客户断开后的异常处理再次发送已发送响应头，抛出 `ERR_HTTP_HEADERS_SENT` 退出；尾随查询因此失败，**本轮是异常中断、未完成性能签收**，不能把 0 条终态观测解释为采集事实绝对丢失。旧 runner 在最后 query 失败前已保存聚合指标和构建 hash，但未保存逐请求样本；入口已修正为 finally 保留样本，避免重犯。

**静态瓶颈线索，非独立量化归因：**SQL.js 的 autoSave 会在提交后同步导出整个数据库，再写文件；可观测采集每条记录涉及持久锁、快照和事实提交等事务，文件扩大后与 HTTP 共用事件循环，增加了整库导出开销。该基线最终数据库约 11.9 MB。本轮没有单独测量这部分占比，不能把全部耗时直接归给导出；也不能靠关闭 autoSave 或改为内存数据库制造达标。PostgreSQL 车道作为独立对照，不覆盖 SQLite 结果。

## 已实施的有限调度修复

此前 collector 每轮至多128条且单文件每次至多16条，outbox每轮32事件，webhook每轮10次投递，但所有批次无论是否有积压都固定等1秒。三个自动循环现在在有进展后用下一次事件循环继续有限批，空闲或失败保留1秒退避；collector继续有界目录扫描，遇EOF半行无进展时退避。达到读取预算但尚未到EOF的半行仍可继续有限读取，不将其误判为空闲。未增大批上限、未增加并发、未修改租约/重试/顺序/授权，停止时仍等待当前批次且不重排。

[调度回归](../../packages/api-nova-api/src/modules/call-observability/call-observability-worker-scheduling.spec.ts)覆盖进展排空、空闲/失败退避、关闭开关、真实 runOnce 活跃批等待与停止重排、EOF半行退避。源码与首次旧构建基线不同，证据分别保存 hash，避免把修复源码误说成已用于旧基线。

## 修复后结果与仍待条件

基线触发的崩溃也已修复：HttpExceptionFilter对响应已发送头、已结束或已断开的情况不再写第二份JSON。真实HTTP部分响应后抛异常、客户端断连等4项回归通过；13项调度回归也全部通过。最终同候选定向回归合计29套/240项通过，API重新构建后才执行下表两轮性能测量。调度/崩溃修复不等于吞吐达标。

两轮顺序执行，期间其他构建、测试、备份演练均暂停。主机 Windows 10.0.19045/x64、Node v24.15.0、Intel Core i7-9750H、12逻辑CPU、34,265,485,312字节内存；没有限制到4核/8GiB参考机，磁盘介质未独立验证。PostgreSQL为16.10，独立随机端口60994，fsync和synchronous_commit均开启。

停止后只读源审计补查另存各目录 `audit-source-summary.json`：SQLite有4124条source记录、sequence范围1～11332内有7208个缺口、547条Gateway finished记录，API日志7219条`RUNTIME_AUDIT_WRITE_FAILED`；PG有6052条、sequence范围1～15004内8952个缺口、1073条Gateway finished记录，日志8956条该标记。源记录范围内缺口和已警告写入失败说明必须连同producer诊断，不能仅等待collector排空后宣布完整。警告同时涵盖排队上限、内存预算与I/O失败，**本轮没有取得逐原因计数，不能将所有标记直接等同于某一失败原因或丢失调用数**。

源码线索包括producer逐record串行mkdir/appendFile、4096待写上限；ingest对每条版本分别持久化writer锁、读快照、正文准备、receipt/事实/投影/事件、释放锁，所有步骤还共享有界串行通道。它们构成下一轮profiling位置，不是本轮已独立量化的单点耗时归因。没有通过增大队列、关闭持久化、删正文或修改门槛宣称解决。

## 默认容量护栏与本轮是否超范围

执行器清理了继承的API_NOVA配置；NODE_ENV=test且未提供显式env文件，应用忽略本地.env。本轮source writer采用代码默认：API_NOVA_AUDIT_MAX_BODY_BYTES每侧16MiB、API_NOVA_AUDIT_MEMORY_BUDGET_BYTES为128MiB，pendingWrites硬上限4096。source writer没有单文件或总磁盘字节上限；独立OBS正文配额开关本轮未启用。不能将OBS后续对象存储配额混同source队列护栏。

4024B响应/0B请求符合正文大小限制。SQLite/PG最终source文件分别12,863,652B/21,831,033B，单条最大7479B/7478B；按已观测最大条长，4096条待写的双倍字节reservation约58.4MiB，但还要加正在采集的captureMemoryBytes（按原始chunk三倍计入），**本轮未导出其峰值，因此无法证明从未瞬时触发128MiB内存预算**。结束后只读测E盘可用2,075,899,777,024B，没有磁盘写满证据；该容量是结束后快照，不是整段磁盘曲线。

正常Gateway+upstream每调用约5条版本事实，本轮100请求/秒即约500条source记录/秒；固定4096条队列在完全不排出时仅容纳约8.2秒。队列溢出保护按设计拒绝继续占用内存，但在参考负载产生事实缺口仍表示吞吐目标没有实现，不能据“护栏工作正常”宣布性能通过。文件总量未触发一个不存在的source磁盘总量门槛，也没有证据要求立即增大默认预算。需先取得queue-drop、budget-drop、实际I/O失败及队列高水位，再决定有界合并写和持久化优化；无法用现有日志准确给出一个保证达标的“最低加大内存值”。
